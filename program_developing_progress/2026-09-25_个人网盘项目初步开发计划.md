# 个人网盘项目初步开发计划

> 文档日期：2026-09-25  
> 当前状态：初步方案，后续将根据开发实践持续修订  
> 项目定位：以 Go 后端为核心的多用户个人网盘，用于求职展示、工程实践和个人使用

## 1. 项目背景与目标

本项目计划从零构建一个简易但完整的个人网盘系统。项目短期用于个人学习和自用，完成核心功能后部署到云服务器，并支持多个用户注册和使用。项目将在个人 GitHub 仓库中开源。

项目的主要目标包括：

1. 通过真实项目深入学习 Go Web 开发、关系型数据库、系统设计和软件工程。
2. 完成一个可运行、可部署、可演示的后端项目，用于求职简历和面试展示。
3. 实现多用户文件存储、文件管理、可靠上传、下载和分享等核心网盘能力。
4. 参考 Cloudreve 的部分后端架构与业务实现，参考 Cloudreve 和 Internxt 的前端界面及操作方式。
5. 在基础网盘稳定后，探索客户端加密和隐私空间等进阶能力。

## 2. 项目范围

### 2.1 首期核心功能

#### 用户与认证

- 用户注册、登录和退出。
- 服务端会话管理，包括过期和主动失效。
- 用户之间的数据隔离。
- 所有文件、文件夹、上传和分享操作均进行身份及资源归属校验。

#### 文件与文件夹管理

- 新建文件夹。
- 文件和文件夹列表。
- 分页、排序和按文件名搜索。
- 文件或文件夹重命名。
- 文件或文件夹移动。
- 文件和文件夹删除。
- 同一目录存在同名对象时，首版拒绝操作并提示用户修改名称。

#### 文件传输

- 普通文件上传和下载。
- 流式读写，避免将大文件完整加载到内存。
- 上传进度和传输状态展示。
- 后续加入分块上传、断点续传、失败重试和过期上传清理。
- 上传完成操作保持幂等，避免重复请求产生重复文件。

#### 容量管理

- 展示用户已使用容量和总容量。
- 支持用户级存储配额。
- 上传前和上传完成时校验配额。
- 处理并发上传可能导致的配额超用问题。

#### 文件分享

- 为文件或文件夹生成分享链接。
- 分享链接可以设置有效期。
- 支持可选提取码或访问密码。
- 支持查看分享状态和主动撤销分享。
- 分享访问由服务端实时校验，撤销或过期后不可继续访问。

#### 文件预览

- 首批支持图片、文本和 PDF 等常见格式。
- 预览功能与下载权限使用同一套访问控制规则。
- 视频转码、Office 在线编辑等复杂能力暂不纳入首版。

### 2.2 隐私能力

基础版本首先实现：

- 用户数据隔离。
- 严格的资源访问控制。
- HTTPS 传输保护。
- 私有文件存储和安全的分享访问。

基础版本不宣称零知识或端到端加密，因为服务端仍可能读取文件内容。

后续可增加独立的“加密隐私空间”：

- 文件在客户端完成加密后再上传。
- 服务端只保存密文和必要元数据。
- 下载后在客户端完成解密。
- 在实现前明确密钥生成、保存、多设备同步、丢失处理和加密分享方案。
- 使用成熟的密码学算法和实现，不自行设计加密算法。

### 2.3 暂不纳入的功能

- 回收站。
- 文件版本历史。
- 面向用户的删除恢复功能。
- 桌面同步客户端。
- 在线协同编辑。
- 复杂的团队、组织和角色权限体系。
- 视频转码及大规模媒体处理。
- 微服务拆分。

删除操作需要在界面中明确提示不可恢复。部署层面的数据库和文件备份仍然需要建设，但它属于系统运维保障，不属于用户回收站功能。

## 3. 产品与开源项目参考

### 3.1 Cloudreve

主要参考：

- Go 网盘项目的整体工程组织方式。
- 文件和文件夹管理业务。
- 上传流程和任务处理。
- 存储驱动抽象与多存储适配思路。
- 文件管理页面与操作交互。

使用方式：

- 不直接复制整个项目。
- 对准备复用的模块先分析其数据库、权限、任务系统和配置依赖。
- 根据复杂度决定直接复用、改造后使用或自行实现。
- 记录代码来源、上游版本、许可证和修改内容。

### 3.2 Internxt

主要参考：

- 简洁的文件管理界面。
- 上传、新建文件夹、列表排序、预览等操作方式。
- 快速分享与高级分享设置。
- 分享密码、权限管理和停止分享的交互设计。
- 客户端加密与隐私保护的产品定位。

前端可研究 Internxt 公开的 Web 客户端源码，但需要检查组件对其 SDK、账号体系和后端接口的依赖，并遵守相应开源许可证。

### 3.3 复用原则

- 复用成熟基础库，不重复实现密码哈希、数据库驱动、对象存储 SDK 等通用能力。
- 核心业务规则需要自己理解并能在面试中解释。
- 项目文档中明确标注外部代码与个人实现的边界。
- 最终项目许可证需要根据实际引入的 GPL、AGPL 或其他许可证代码确定。

## 4. 技术方案

### 4.1 初步技术选型

| 层面 | 初步选型 | 说明 |
| --- | --- | --- |
| 后端语言 | Go | 项目学习与求职展示的核心语言 |
| HTTP 框架 | Gin | 入门成本适中，便于理解路由、中间件和 HTTP 请求处理 |
| 系统架构 | 模块化单体 | 适合单人开发和首期云端部署 |
| 数据库 | PostgreSQL | 用于学习约束、索引、事务和并发控制 |
| 数据访问 | 显式 SQL 或轻量查询工具 | 优先理解 SQL 和事务，再决定是否引入 ORM |
| 前端 | React + TypeScript | 便于参考 Cloudreve 与 Internxt，主要负责接口对接和交互呈现 |
| API 契约 | OpenAPI | 统一请求结构、响应结构、错误码和鉴权方式 |
| 文件存储 | 本地磁盘起步 | 后续接入 S3 兼容对象存储 |
| 部署 | Docker Compose + HTTPS 反向代理 | 保证本地和云服务器环境可复现 |

Redis、消息队列和服务注册等组件不作为首版基础依赖。只有在明确出现缓存、异步任务吞吐或服务拆分需求时再引入。

### 4.2 Gin 与未来框架迁移

首版使用 Gin，但业务逻辑不直接依赖 Gin：

- HTTP 层负责参数解析、身份信息提取、业务调用和响应转换。
- 业务层使用标准库 `context.Context`，不接收 `*gin.Context`。
- 数据访问模型、HTTP 请求模型和业务对象适当分离。
- 业务错误由 HTTP 层统一映射为状态码和响应体。
- 文件存储通过清晰的存储接口与业务层连接。

这样做可以降低将来迁移到 go-zero 或其他框架时的改造范围。框架迁移并不天然等于系统升级，不预先安排全量重写。后续只有在代码生成、RPC、服务治理或团队规范等需求明确出现时，再评估 go-zero。也可以先迁移一个边界清晰的模块，比较实际收益后再决定是否扩大范围。

### 4.3 分层结构

```text
前端 Web 应用
    ↓ HTTP / OpenAPI
HTTP 接口层
    ↓
业务服务层
    ├── 用户与认证
    ├── 文件与目录
    ├── 上传与配额
    └── 分享与访问控制
    ↓
数据访问层 / 文件存储抽象
    ├── PostgreSQL
    ├── 本地文件系统
    └── S3 兼容对象存储（后续）
```

模块化单体意味着所有模块首期运行在同一个 Go 服务中，但代码边界保持清晰。后续即使不拆微服务，也可以独立维护和测试各个业务模块。

## 5. 初步数据模型

| 数据对象 | 主要职责 |
| --- | --- |
| `users` | 用户身份、密码摘要、状态、容量配额和已用容量 |
| `sessions` | 登录会话、过期时间、撤销状态和客户端信息 |
| `nodes` | 文件及文件夹的名称、类型、所有者、父目录和当前状态 |
| `objects` | 实际文件内容的存储键、大小、校验值和存储类型 |
| `upload_sessions` | 上传任务、文件信息、已上传大小、状态和过期时间 |
| `upload_parts` | 分块上传的分块编号、大小、校验值和状态 |
| `shares` | 分享对象、访问令牌、提取码摘要、有效期和撤销状态 |
| `jobs` | 临时文件清理、失效上传清理等需要重试的后台任务 |

用户看到的文件目录与物理存储位置分离。例如，用户看到的 `/学习/Go笔记.pdf` 由 `nodes` 表描述；实际文件以服务端生成的存储键保存在磁盘或对象存储中。这样可以降低重命名和移动操作的成本，也便于以后更换存储后端。

首版不实现文件历史版本，也不做跨用户内容去重。

## 6. 关键业务规则

### 6.1 权限规则

- 用户只能访问自己拥有的文件和文件夹，或通过有效分享获得访问权限。
- 权限校验不能只依赖前端隐藏按钮，必须在每个后端接口中执行。
- 文件标识不可作为访问凭证，即使用户猜到其他文件 ID 也不能越权访问。

### 6.2 文件删除

- 删除为不可恢复操作，前端需进行明确确认。
- 数据库记录删除和物理文件删除需要设计可靠的一致性流程。
- 物理文件删除失败时，由后台任务记录并重试。
- 删除文件夹前需要定义递归删除、非空目录处理和并发操作规则。

### 6.3 上传

- 上传任务必须属于当前用户。
- 分块只能写入对应的上传任务。
- 完成上传前校验分块、文件大小、校验值和容量配额。
- 完成请求需要保持幂等，重复提交不能生成多个文件节点。
- 失败或过期的上传临时文件需要定期清理。

### 6.4 分享

- 分享链接对应独立的数据库记录，不直接暴露文件存储地址。
- 每次访问校验分享是否存在、是否撤销、是否过期以及提取码是否正确。
- 撤销分享只能阻止未来访问，无法收回对方已经下载的文件。

## 7. 分阶段开发计划

### 阶段 0：需求和设计

交付内容：

- 首版需求清单。
- 核心业务规则。
- 数据库实体关系设计。
- API 草案。
- 主要页面草图。
- 关键架构决策记录。

验收标准：

- 明确首版做什么和不做什么。
- 可以完整描述“登录后创建目录、上传文件并下载”的业务流程。
- 可以说明用户隔离、同名冲突和删除的处理规则。

### 阶段 1：工程基础与用户认证

交付内容：

- Go 工程目录和配置系统。
- Gin 服务启动与优雅关闭。
- PostgreSQL 连接和数据库迁移。
- 用户注册、登录、退出和会话校验。
- 统一响应、错误处理、日志和请求 ID。
- 初始 OpenAPI 文档。

学习重点：

- Go Web 请求生命周期。
- Gin 路由和中间件。
- 密码安全和会话管理。
- 配置、日志、错误与依赖组织。

验收标准：

- 用户可以注册并登录。
- 登录会话过期或退出后无法继续访问受保护接口。
- 接口错误具有稳定、可识别的响应格式。

### 阶段 2：多用户文件管理闭环

交付内容：

- 新建和浏览文件夹。
- 普通文件上传和流式下载。
- 重命名、移动、删除、分页、排序和搜索。
- 用户容量统计和基础配额。
- 最小可用的前端文件管理页面。

学习重点：

- SQL 查询、索引和事务。
- 流式文件 I/O。
- 资源归属与越权防护。
- 数据库元数据与物理文件的一致性。

验收标准：

- 两个用户无法访问或修改彼此的文件。
- 大文件上传下载不会导致服务内存随文件大小等比例增长。
- 文件移动和重命名遵守同目录重名规则。

### 阶段 3：可靠上传

交付内容：

- 分块上传。
- 上传暂停和断点续传。
- 分块校验和文件合并。
- 上传任务状态机。
- 失败重试、幂等完成和临时文件清理。
- 并发上传下的配额控制。

学习重点：

- 幂等设计。
- 状态机。
- 并发控制和事务隔离。
- 故障恢复和后台任务。

验收标准：

- 网络中断后可以继续上传未完成的内容。
- 重复上传分块或重复完成请求不会破坏数据。
- 过期上传产生的临时数据可以被可靠清理。

### 阶段 4：分享、预览与产品体验

交付内容：

- 分享链接、提取码、有效期和撤销功能。
- 分享管理页面。
- 图片、文本和 PDF 基础预览。
- 上传队列、进度、失败原因和重试交互。
- 容量展示和关键操作反馈。
- 融合 Cloudreve 与 Internxt 风格的前端界面。

学习重点：

- 公开访问入口的安全控制。
- 前后端 API 契约。
- 文件类型识别和安全响应头。
- 可理解的错误信息和状态反馈。

验收标准：

- 分享过期或撤销后立即失效。
- 提取码不以明文保存。
- 不支持预览的文件仍可在有权限时下载。

### 阶段 5：云端部署与工程完善

交付内容：

- Docker 镜像和 Docker Compose 环境。
- 云服务器部署。
- 域名和 HTTPS。
- 结构化日志、基础指标和健康检查。
- 数据库与文件存储备份流程。
- 基础压力测试和性能记录。
- 完整 README、部署文档和演示说明。

学习重点：

- Linux 服务部署。
- 容器化、反向代理和 TLS。
- 可观测性、备份和故障排查。
- 容量规划和性能瓶颈定位。

验收标准：

- 新环境可以按照文档完成部署。
- 系统具备健康检查和关键错误日志。
- 备份流程经过至少一次实际恢复验证。
- 性能报告注明环境、数据规模、测试方法和结论。

### 阶段 6：加密隐私空间

交付内容：

- 明确的安全目标与威胁模型。
- 客户端文件加密和下载解密。
- 密钥生成、保存和多设备使用方案。
- 加密文件的分块上传与完整性校验。
- 清楚说明密钥丢失后的恢复边界。

学习重点：

- 端到端加密的信任边界。
- 密钥生命周期管理。
- 加密、分块、续传、预览和分享之间的取舍。

验收标准：

- 服务端无法直接读取加密空间中的文件内容。
- 密钥和明文不会写入服务端日志。
- 安全说明与实际实现一致，不夸大为未经验证的零知识系统。

## 8. 测试与质量保障

重点测试场景包括：

- 未登录访问和失效会话访问。
- 用户通过构造文件 ID 尝试越权访问。
- 同名文件及同名文件夹冲突。
- 文件上传中断、分块重复和完成请求重复。
- 并发上传导致的配额竞争。
- 文件移动产生目录循环。
- 数据库操作成功但文件操作失败，或文件操作成功但数据库操作失败。
- 分享过期、撤销和错误提取码。
- 路径穿越、恶意文件名和不可信文件类型。

测试以关键业务规则、故障边界和安全问题为重点，不为简单的数据结构读写编写重复价值较低的测试。

- 关键架构决策及其取舍。

- 本地开发和云端部署文档。

- 开源代码复用清单与个人实现说明。
- 线上演示地址和可复现的演示账号方案。

面试时重点讲解：

- 为什么从模块化单体开始。
- 如何保证用户之间的数据隔离。
- 如何实现上传状态机、幂等和断点续传。
- 如何协调数据库元数据与文件存储的一致性。
- 为什么基础版本与端到端加密空间分阶段实现。
- 框架迁移时哪些代码可以保留，哪些代码需要重写。

## 10. 开发与学习方式

每个核心模块按照以下流程推进：

1. 明确真实业务场景和验收标准。
2. 分析数据模型、接口和异常情况。
3. 解释设计选择及其代价。
4. 实现最小可运行版本。
5. 使用测试或实际操作验证关键规则。
6. 记录问题、结论和下一步改进。

开发过程中以后端为重点。前端主要用于完成产品交互和验证接口，重点理解请求响应、鉴权、上传协议、分页排序、错误处理和任务状态，无需投入同等深度研究复杂前端工程。
